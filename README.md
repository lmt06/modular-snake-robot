# Modular Snake Robot: Neuroevolution in MuJoCo

Can a controller built from identical, locally connected modules keep a snake robot swimming when its body changes length?

This project evolves neural controllers for a multi-segment swimming snake (Gymnasium's `Swimmer-v5`, simulated in MuJoCo) and compares two designs:

- **Centralized:** one network sees every joint's angle and angular velocity and outputs every joint's torque. Its size depends on the number of joints, so it has to be evolved separately for each body length.
- **Modular:** one small network (49 weights) is copied at every joint. Each copy sees its own joint's angle and velocity plus its neighbors' angles, and outputs its own torque. Because the weights are shared, a genome evolved on one body can be transplanted onto bodies of any length.

Controllers were evolved with a genetic algorithm (EvoTorch), using forward distance swum in 40 seconds as fitness. Modular controllers evolved on a 5-segment body were then tested, without retraining, on 3-, 8-, and 10-segment bodies.

![GIF of snake swimming](sine_n5.gif)

## Key result

On longer bodies (8 and 10 segments), the modular controller evolved at 5 segments swam about as far as it did on its training body (around 13 units), outperforming centralized controllers evolved specifically for those lengths (around 10 units). Shrinking the body to 3 segments hurt transfer, where the centralized controller did much better. Results are from 5 evolutionary runs per condition, with large seed-to-seed variation.

## Files

| File | What it does |
|---|---|
| `swimmer_n3.xml`, `swimmer_n5.xml`, `swimmer_n8.xml`, `swimmer_n10.xml` | MuJoCo body files for snakes with 3, 5, 8, and 10 segments |
| `controller.py` | The centralized and modular neural networks: input selection, genome size, decoding, and computing torques |
| `fitness.py` | Runs a genome in the simulator and returns the average forward distance |
| `evolve.py` | Evolves a controller with EvoTorch's genetic algorithm and saves the best genome and fitness curves |
| `baseline.py` | Scores 100 random genomes to get a random-controller baseline |
| `transfer.py` | Tests evolved modular genomes on body lengths they weren't trained on |
| `watch.py` | Replays a saved genome in a window, or saves it as a GIF |
| `plot_curves.py` | Plots fitness over generations for one or more runs |
| `plot_transfer.py` | Plots distance vs. body length for modular and centralized controllers |
| `sine_gif.py` | Hand-designed traveling-wave (sine) controller, used as a baseline |

## Example commands

**Evolve a controller** (saves `<output>.npy` and `<output>_curves.npz`):
```
python evolve.py --controller modular --xml ./swimmer_n5.xml --episodes 3 --seed 1 --output mod_n5_s1
python evolve.py --controller central --xml ./swimmer_n8.xml --episodes 3 --seed 1 --output central_n8_s1
```
Options: `--popsize` (default 30), `--gens` (default 80), `--mut_stdev` (default 0.2).

**Random baseline:**
```
python baseline.py --controller central --xml ./swimmer_n5.xml --output baseline_central_n5
```

**Watch a saved genome, or save a GIF:**
```
python watch.py mod_n5_s1.npy --controller modular --xml ./swimmer_n8.xml
python watch.py mod_n5_s1.npy --controller modular --gif mod_n5_s1.gif
```
Note: the `./` before the XML file name is required.

**Test transfer** (edit the seeds, body files, and genome names at the top of the script first):
```
python transfer.py
```

**Plot fitness curves for several seeds:**
```
python plot_curves.py mod_n5_s1 mod_n5_s2 mod_n5_s3 mod_n5_s4 mod_n5_s5 --title "Modular controller, N=5" --output mod_n5_curves.png
```

**Plot transfer results:**
```
python plot_transfer.py transfer_n3.npz transfer_n8.npz transfer_n10.npz --output transfer.png
```

**Hand-designed sine-wave baseline GIF:**
```
python sine_gif.py
```

## Background

Built as the final project for ECE497: Evolutionary Robotics at Rose-Hulman Institute of Technology (Fall 2026). Inspired by Yim et al. (2007), *Modular Self-Reconfigurable Robot Systems: Challenges and Opportunities for the Future*, which argues that modular robots should keep working when modules are added or removed.
